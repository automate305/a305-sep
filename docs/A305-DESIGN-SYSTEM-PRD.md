## 0. How to use this document

This PRD exists so that wireframes start from something instead of a blank canvas. Drop it into a wireframing tool (or hand it to a designer or an AI agent) and it should be enough to produce first-pass screens without re-deriving decisions.

Read in this order when wireframing:

1. **§3 Design principles** — the rules every screen must obey.
2. **§5 Key components** — the vocabulary you are allowed to use.
3. **§7 Screen inventory & layout templates** — the skeletons to start from.
4. **§8 State matrix** — every status the UI must be able to show.

Everything else is context and acceptance criteria.

## 1. Background

### 1.1 What exists today

Automate305 runs a multi-brand outbound engine (`a305-sep`): Supabase for state, SMTP providers for sending, Vercel for the API, and a single-page **Operator Dashboard** at `public/dashboard.html`. That dashboard already carries an implicit design language:

- Dark-first palette with a light mode via `prefers-color-scheme`.
- One green accent (`#34d399`) used for "healthy / live / go", plus amber, red, blue, and violet semantic colors.
- 14px radius cards, uppercase 11–12.5px muted section labels, tabular-nums for every number.
- A handful of hand-rolled components: KPI tile, card, badge, pill, warmup bar, health score, table, row list, hold-queue item with actions, key gate.

The problem: all of it lives as ad-hoc CSS classes inside one HTML file. Nothing is named, tokenized, or documented. Every new screen (client reports, sequence editor, warmup planner, prospect list views) would re-invent it slightly differently.

### 1.2 Why a design system now

- **Speed.** Wireframes and prototypes should be assembled from known parts, not drawn from scratch.
- **Consistency across surfaces.** The same status ("BLOCKED", "HELD", "DRAFT") must look identical in the operator dashboard, a client PDF, and a Slack card.
- **Multi-brand by design.** The engine already sends for two brands (`automate305`, `aestheticdevicepro`). The UI must treat brand as a first-class dimension, not a color hack.
- **AI-buildable.** Most new screens will be generated by AI agents. A system with explicit tokens, component names, and state rules makes generated output predictable and reviewable.

## 2. Goals & non-goals

### 2.1 Goals

| # | Goal | Success signal |
|---|------|----------------|
| G1 | Cut time-to-first-wireframe for a new screen to under 30 minutes | New screens are assembled from §5 components and §7 templates without inventing new patterns |
| G2 | One source of truth for tokens (color, type, spacing, radius, elevation) | `dashboard.html` refactored to consume tokens; zero hard-coded hex values outside the token file |
| G3 | Every domain state in §8 has a defined visual treatment | State matrix is 100% covered; no "unknown status" fallbacks in the UI |
| G4 | Light and dark parity | Every component passes contrast checks in both themes (WCAG AA for text, 3:1 for UI chrome) |
| G5 | Brand-aware without brand-specific components | Brand is expressed via a badge and a scoped accent token, never via forked components |
| G6 | Client-safe output | A subset of components ("Report tier") is defined that can be shown to a client with no internal jargon (no "kill switch", no "seed mode") |

### 2.2 Non-goals (v1)

- Building a React/Vue component library. v1 is **tokens + CSS + HTML patterns + documentation**. A framework port is a later phase.
- Marketing website redesign. The system must be usable there, but the site is not a v1 deliverable.
- Iconography beyond a small utility set (status dot, chevron, external link, refresh, lock, warning).
- Motion design beyond basic transitions (hover, expand/collapse, toast in/out).
- Data visualization library. Charts follow the token palette but chart specs are a separate PRD.

## 3. Design principles

These are the tie-breakers. When two layouts both "work", pick the one that honors the higher-numbered principle less and the lower-numbered one more.

### P1. Status before decoration
The operator's first question is always "is anything on fire?" Every screen leads with health and blockers: kill switch, held items, blocked mailboxes, failed sends. Decorative elements never compete with a status signal.

### P2. Numbers are the interface
This is a sending engine. Counts, caps, rates, and scores are the primary content. All numerics use tabular figures, right-align in tables, and carry their unit or denominator (`12/25`, `85`, `2.1%`). A number without context is a bug.

### P3. Dark-first, light-parity
Operators run this at 6 a.m. before the daily trigger and again at night. Dark is the default. Light mode is a full peer, not an afterthought, and both are driven from the same token names.

### P4. One accent, semantic everything else
Green is the single brand accent and means exactly one thing: healthy / live / go. Amber means attention, red means stop or failure, blue means link or informational, violet is reserved for the secondary brand. No color is used purely for decoration.

### P5. Density with breathing room
Operators want a lot on one screen. Default to compact rows (8px vertical padding) inside cards with generous outer gutters (16–20px). Never introduce a second level of nested cards.

### P6. Reversible by default, destructive by exception
"Approve", "Skip", "Refresh" are one-click. "Kill switch", "Archive sequence", "Suspend mailbox" require a confirm step and use the danger treatment. The danger treatment is never used for anything that is not actually destructive.

### P7. Brand is a dimension, not a theme
Every entity (mailbox, sequence, campaign, queue item) belongs to a brand. Brand is shown with a badge and, optionally, a scoped accent. The layout and components are identical across brands.

### P8. Plain language, operator vocabulary
Labels use the words the operator uses: "Held", "Warming", "Blocked", "Sent today". Internal names (`send_mode`, `daily_cap`) are translated at the label layer. Client-facing surfaces go one step further and drop engine jargon entirely (see §6.3, Report tier).

### P9. Empty and error states are designed, not defaulted
Every list has an intentional empty state with a next action ("No mailboxes warming up. Add one from Senders."). Errors say what failed and what to do, never just "Something went wrong".

### P10. Build for generation
Components have stable names, minimal required props, and documented variants so that an AI agent can produce correct markup from the name alone. If a component needs a paragraph to explain, it needs to be split.

## 4. User personas

### 4.1 Cam — Founder / Operator (primary)

- **Role:** Runs Automate305 solo today. Owns strategy, sales calls, and the daily send trigger.
- **Context:** Checks the dashboard on a laptop first thing and on a phone between site visits and prospect calls in Brickell and the greater Miami metro. Also holds a Florida Licensed Mold Assessor license, so restoration outreach is a warm channel and needs its own campaign view soon.
- **Jobs to be done:**
  - "Is sending healthy right now, and is anything held or blocked?"
  - "Which mailboxes are warming, and when will they graduate?"
  - "Which sequence is actually producing replies, per brand?"
  - "Approve or skip what the AI flagged before it goes out."
- **Pain today:** Everything is in one long page; must scroll to find the hold queue; no mobile layout; status names differ between the schema, the API, and the UI.
- **Design implications:** Status-first header, sticky brand switcher, mobile stacking, hold queue promoted above the fold when non-empty.

### 4.2 Future ops hire / VA — Campaign Manager

- **Role:** Part-time operator who enrolls contacts, manages replies, and monitors warmup. Not a developer.
- **Context:** Works from a browser; may never open the terminal or Supabase.
- **Jobs to be done:**
  - Enroll a cleaned prospect list into the right sequence and A/B slot.
  - Mark replied / bounced / unsubscribed without curl commands.
  - Read a mailbox health breakdown and know whether to raise the cap.
- **Design implications:** Forms and confirmations for every action currently done via API; inline help on health score composition; guardrails (cannot activate a DRAFT sequence).

### 4.3 Client — HVAC / Home-services owner-operator

- **Role:** Owner of a 3–25 person HVAC, roofing, plumbing, electrical, or restoration company in South Florida. Automate305 runs outbound and automation for them.
- **Context:** Reads a weekly report on a phone, often between jobs. Cares about booked calls and replies, not deliverability internals.
- **Jobs to be done:**
  - "How many conversations did this generate this week?"
  - "What is the next step and what do you need from me?"
- **Design implications:** The **Report tier** (§6.3): large KPI tiles, plain-English labels, no engine jargon, brand-scoped to their company, print- and PDF-friendly light theme.

### 4.4 Builder — Developer or AI agent

- **Role:** Whoever produces the next screen. Increasingly an AI agent working from a prompt.
- **Jobs to be done:**
  - Produce a correct, on-system screen from a short spec.
  - Add a new status without touching ten files.
- **Design implications:** Token file, named components, documented variants, state matrix, and the layout templates in §7. Everything expressed as copy-pasteable HTML/CSS in v1.

## 5. Key components

Components are grouped into **Foundations** (tokens), **Primitives**, **Data display**, **Domain components**, and **Patterns**. Names are the canonical names to use in wireframes, code, and prompts.

### 5.1 Foundations (tokens)

Token names are fixed. Values below are the v1 defaults, lifted from the current dashboard and normalized.

#### Color — surface & text

| Token | Dark | Light | Use |
|---|---|---|---|
| `--bg` | `#0b0f14` | `#f4f6f9` | Page background |
| `--panel` | `#141a22` | `#ffffff` | Card / panel surface |
| `--panel-2` | `#1b2230` | `#f7f9fc` | Inputs, secondary buttons, bar tracks |
| `--border` | `#232c3a` | `#e3e8ef` | All hairlines |
| `--text` | `#e8edf4` | `#0f1722` | Primary text |
| `--muted` | `#8b98ab` | `#5a6b81` | Labels, secondary text |
| `--faint` | `#5c6a7e` | `#8595aa` | Timestamps, disabled, tertiary |

#### Color — semantic

| Token | Dark | Light | Meaning |
|---|---|---|---|
| `--accent` | `#34d399` | `#0f9d6b` | Healthy / live / go / primary action |
| `--accent-dim` | `#0f2e26` | `#e4f7ef` | Accent background tint |
| `--warn` | `#f5b445` | `#b7791f` | Attention, warming, held, capped |
| `--warn-dim` | `#3d2e0a` | `#fdf3dd` | Warn background tint |
| `--danger` | `#f87171` | `#c53030` | Failure, blocked, stopped, destructive |
| `--danger-dim` | `#2a1414` | `#fdecec` | Danger background tint |
| `--info` | `#5aa2ff` | `#2b6cb0` | Links, informational |
| `--brand-2` | `#a78bfa` | `#6b46c1` | Secondary brand (aestheticdevicepro) |
| `--brand-2-dim` | `#1a1630` | `#f0ecff` | Secondary brand tint |

Rule: no hex value appears outside the token file. Brand badges consume `--accent` (Automate305) or `--brand-2` (secondary brand); adding a third brand means adding a `--brand-3` pair, not a new component.

#### Typography

| Token | Value | Use |
|---|---|---|
| `--font` | system stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`) | Everything |
| `--fs-xs` | 11px / uppercase / +0.5px tracking | Section labels, table headers, pills |
| `--fs-sm` | 12–12.5px | Meta, timestamps, help text |
| `--fs-base` | 13–14px / 1.5 | Body, table cells |
| `--fs-lg` | 17–18px / 650 weight | Page title, gate title |
| `--fs-kpi` | 26px / 680 weight / -0.5px tracking | KPI numbers |
| `--fs-metric` | 20px / 650 weight | Secondary metrics |

Numbers always set `font-variant-numeric: tabular-nums`.

#### Spacing, radius, elevation

| Token | Value |
|---|---|
| `--space-1..6` | 4, 8, 12, 16, 20, 24px |
| `--radius-sm` | 6px (pills, badges, steps) |
| `--radius-md` | 9–10px (buttons, inputs) |
| `--radius-lg` | 14px (cards, KPI tiles, gate) |
| `--radius-full` | 99px (bars, dots) |
| `--shadow-focus` | `0 0 0 4px var(--accent-dim)` (status dot halo, focus ring) |

No drop shadows in v1. Elevation is expressed by surface step (`--bg` → `--panel` → `--panel-2`) and a hairline border.

#### Breakpoints

| Name | Width | Behavior |
|---|---|---|
| `mobile` | < 600px | Single column, KPIs 2-up, tables become row lists |
| `tablet` | 600–860px | Single column, KPIs auto-fit |
| `desktop` | > 860px | Two-column grid `1.35fr 1fr`, max width 1280px |

### 5.2 Primitives

| Component | Variants | Notes |
|---|---|---|
| **Button** | `default`, `ghost`, `active`, `primary`, `danger`, sizes `sm` / `md` | `primary` = accent fill, dark text. `danger` requires confirm step (P6). |
| **Input** | text, password, select, textarea; states default / focus / error / disabled | Full width inside forms. Error message slot below. |
| **Badge** | `brand` (per brand token), `neutral` | Uppercase, 10.5px. Identifies which brand an entity belongs to. |
| **Pill** | `accent`, `warn`, `danger`, `info`, `off` | Status chips. Text = the status word, never an icon alone. |
| **Status Dot** | `on` (accent, halo), `off` (danger, halo) | Global engine state in the header. |
| **Divider row** | — | Hairline between list rows; first row has none. |
| **Section label** | with optional count `· 12` | Uppercase muted h2 inside cards. |
| **Timestamp** | relative (`3m ago`) with absolute title | Faint, no-wrap. |

### 5.3 Data display

| Component | Description | Wireframe note |
|---|---|---|
| **KPI Tile** | Big number + uppercase label. Variants `neutral`, `accent`, `warn`, `bad`. | Grid `auto-fit, minmax(130px, 1fr)`. Max 8 per row. |
| **Card** | Panel with section label, optional count, body. | Never nest cards. |
| **Data Table** | Header row, right-aligned numeric columns, optional badge column. | On mobile collapses to **Row List**. |
| **Row List** | Primary line (`.em`, ellipsized) + meta line + trailing slot. | Default for entities: mailbox, contact, queue item. |
| **Progress Bar** | 6px track, accent fill; `full` variant turns amber. | Always paired with `n/cap` caption. |
| **Score** | Integer 0–100, color by threshold: ≥85 good, 60–84 ok, <60 bad. | Optional segmented breakdown bar and detail lines. |
| **Metric Pair** | Label + large value, 2-up grid. | AI spend, rates. |
| **Empty State** | Faint centered text + next action. | Required for every list (P9). |

### 5.4 Domain components

Built from the above; these are the reusable blocks that make wireframes fast.

| Component | Composition | Data |
|---|---|---|
| **Engine Header** | Status Dot + title + subtitle + timestamp + Refresh + Lock | `kill_switch`, `generated_at` |
| **Brand Switcher** | Button group: All brands + one per brand (`active` variant on selection) | `brands[]` |
| **KPI Strip** | KPI Tiles: Sent today, Queued, Held (warn if >0), Active, Replied, Completed, Contacts, Unsubscribed, Bounced, + STOPPED tile when kill switch on | `kpis{}` |
| **Pipeline Table** | Data Table: Sequence · Brand badge · Active · Replied · Done · Total | `pipeline_summary` |
| **Mailbox Row** | Row List: address, status pill (WARMING/WARM/BLOCKED/SUSPENDED), mode pill (LIVE/SEED), Score, Progress Bar + `sends/cap` | `mailboxes[]` |
| **Health Breakdown** | Score + segmented bar + 5 detail lines (inbox placement /40, bounce /20, complaint /20, postmaster /10, reply /10) + cap warning | `health_scores[0]` |
| **Warmup Card** | Row List: address, "Day N of warmup · Cap · Mode", Score, projected graduation date; BLOCKED line in danger | `warming[]` |
| **Hold Item** | Row: recipient, sequence/step, amber reason line, actions Approve / Skip | `hold_queue[]` |
| **Queue Row** | Row: recipient, step chip, scheduled time | `queue[]` |
| **Activity Row** | Row: recipient, step chip, status chip (sent/failed), timestamp | `recent[]` |
| **Key Gate** | Centered card, password input, primary button, error slot | — |
| **Kill Switch Control** | Danger button + confirm dialog + resulting STOPPED tile / off dot | `global_settings.kill_switch` |
| **Sequence Lifecycle** | Stepper DRAFT → APPROVED → ACTIVE (→ ARCHIVED), with gated actions | `sequences.status` |

### 5.5 Patterns

| Pattern | Rule |
|---|---|
| **Confirm dialog** | Required for danger actions. Title states the consequence ("Stop all sending?"), body names the scope, buttons are `ghost` Cancel + `danger` Confirm. |
| **Toast** | Bottom-right on desktop, top on mobile. Accent for success, danger for failure. Auto-dismiss 4s; failure persists until dismissed. |
| **Inline error** | Red 12.5px line below the field or above the list. Names the failure and the fix. |
| **Loading** | Skeleton rows in the same height as the real rows. Never a full-page spinner. |
| **Grouping by brand** | Lists that span brands group under a brand badge header, sorted by slug. |
| **Auth gate** | Any secured page shows the Key Gate first; key stored in `localStorage` only. |

## 6. Tiers

Three tiers control which components and vocabulary may appear on a surface.

### 6.1 Operator tier
Everything in §5. Internal vocabulary allowed. Dark default.

### 6.2 Manager tier
Operator tier minus Kill Switch Control and raw provider/DNS internals. Adds forms for enroll, update-status, hold-queue actions, and sequence approval. Inline help required on Score and Warmup Card.

### 6.3 Report tier (client-facing)
Allowed: KPI Tile, Card, Data Table, Metric Pair, Section label, Timestamp, Empty State, Brand badge (client's own brand only).
Not allowed: Pill statuses with engine words, Score breakdown, Warmup, Hold queue, Kill switch, any mention of mailboxes or send modes.
Vocabulary mapping: `replied` → "Conversations", `sent` → "Outreach delivered", `active` → "In progress", `bounced`/`unsubscribed` → omitted from the client view. Light theme default, print stylesheet required.

## 8. State matrix

Every status the engine emits and the treatment it must receive. Wireframes must show at least one instance of each state that applies to the screen.

### 8.1 Engine

| State | Treatment |
|---|---|
| Running | Status Dot `on`, no STOPPED tile |
| Kill switch on | Status Dot `off`, KPI Tile `bad` "STOPPED / Kill switch", banner above KPI Strip |

### 8.2 Mailbox (`mailboxes.status`, `send_mode`)

| State | Pill | Extra |
|---|---|---|
| `WARMING` | warn | Appears in Warmup Card with day count and projection |
| `WARM` | accent | — |
| `BLOCKED` | danger | Danger line "BLOCKED: score below graduation threshold" |
| `SUSPENDED` | off | Address rendered in `--faint` |
| `LIVE` mode | accent, tinted | — |
| `SEED` mode | warn | — |
| inactive (`active=false`) | off pill "inactive" | No progress bar |
| cap reached | Progress Bar `full` (amber) | Caption stays `n/cap` |

### 8.3 Health score

| Range | Class | Color |
|---|---|---|
| 85–100 | good | accent |
| 60–84 | ok | warn |
| 0–59 | bad | danger |
| null | — | Pill `off` "no score" |
| seed test missing | — | Warn line "Score capped at 60: seed test required" |

### 8.4 Sequence (`sequences.status`)

| State | Pill | Allowed actions |
|---|---|---|
| `DRAFT` | off | Approve |
| `APPROVED` | info | Activate |
| `ACTIVE` | accent | Archive (danger, confirm) |
| `ARCHIVED` | off, strikethrough name | none |

There is no path from DRAFT to ACTIVE. The stepper must make this visually obvious.

### 8.5 Queue item (`send_queue.status`)

| State | Chip | Where |
|---|---|---|
| `PENDING` | neutral | Today's Queue |
| `HELD` | warn | Hold Queue, with reason and actions |
| `SENDING` | info, pulsing dot | Today's Queue |
| `SENT` | accent | Recent Activity |
| `FAILED` | danger | Recent Activity, persists at top |
| `SKIPPED` | off | Recent Activity |
| `EXPIRED` | off, with timestamp | Recent Activity |

### 8.6 Enrollment (`enrollments.status`)

| State | Report-tier label | Operator chip |
|---|---|---|
| `active` | In progress | accent |
| `completed` | Sequence finished | neutral |
| `replied` | Conversation | accent, bold |
| `unsubscribed` | (hidden) | off |
| `bounced` | (hidden) | danger |

### 8.7 Brand

| Brand slug | Badge token |
|---|---|
| `automate305` | `--accent` / `--accent-dim` |
| `aestheticdevicepro` | `--brand-2` / `--brand-2-dim` |
| any new brand | new `--brand-N` pair; same Badge component |

## 9. Content & copy rules

- Sentence case for everything except Section labels, table headers, pills, and badges (uppercase by style, not by typing).
- Status words are shown exactly as the enum, in uppercase, in the operator tier. They are translated in the report tier (§6.3).
- Numbers: thousands separators, no decimals on counts, one decimal on rates, always with `%` or `/cap`.
- Relative time for anything under 24h, date for anything older; absolute timestamp on hover.
- Empty states name the next action and, where possible, link to it.
- Error copy pattern: **what failed** + **what to do**. "Could not load dashboard. Check the key and try again."
- Never use "Something went wrong", "Oops", or exclamation points.

---

## 10. Accessibility requirements

- Text contrast ≥ 4.5:1 and UI chrome ≥ 3:1 in both themes; tokens are validated, not individual screens.
- Status is never conveyed by color alone: every Pill, Chip, and Score carries the word or number.
- All interactive elements reachable by keyboard with a visible focus ring (`--shadow-focus`).
- Tables have real `<th>` headers; row lists on mobile preserve reading order.
- Minimum touch target 40×40px on mobile for Approve / Skip and the Brand Switcher.
- Respect `prefers-reduced-motion`: no pulsing `SENDING` dot, no toast slide.
